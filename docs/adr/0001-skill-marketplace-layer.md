# Skill Marketplace Layer

Add a `SkillMarketplace` service as an independent layer on top of the existing Skill discovery pipeline, changing SkillHub from "pull all at startup" to "list metadata + install on demand", and adding GitHub/Gitee repository skill sources. Installed skills persist to `loongcode.jsonc` `skills.paths` and re-enter the existing `SkillV2` consumption chain as `DirectorySource` entries.

## Considered Options

- **New `SkillMarketplace` service (chosen)**: Preserves the existing SkillHub and `discoverSkills` orchestration. The marketplace only fetches metadata for browsing; file downloads happen on install. GitHub repos are addable via config write-back.
- **Modify SkillHub to on-demand**: Rewrite `pullAll` to `list` + `install`. Breaks the existing startup-time full-pull behavior that other code may depend on.
- **Extend `SkillV2.Source` union with `RepoSource`**: Would require modifying the core `Source` schema and `load()` logic. Mixes marketplace concerns into the runtime context layer.

## Consequences

- `SkillHub.pullAll()` is no longer called at startup; the `discoverSkills` orchestrator now only scans local (already-installed) skills. The SkillHub wiring was removed entirely from `skill/index.ts`.
- Config write-back keeps the existing `config.updateGlobal` helper. A dedicated `ConfigWriter` service was considered but rejected so as not to add a new service for what is a single write-backed mutation; `jsonc-parser`/`Flock` can be adopted later if more config-editing features appear.
- Repo-add validates the URL against the host's branch API before persisting; a `404` (missing repo) is rejected, while timeouts/network errors are admitted so transient network failures do not block adding a known-good repo.
- Repo tarballs and the SkillHub catalogue are cached in memory for 5 minutes via per-key `Effect.cachedWithTTL` wrappers, which also deduplicate concurrent in-flight fetches. Repo entries are keyed by their configured URL and cached **after** gunzip/parse, so repeat `list()`/`install()` calls neither re-download nor re-decompress; `addRepo`/`removeRepo` need no explicit invalidation because the URL is the cache key (a removed repo's stale entry is simply unreachable). SkillHub catalogue responses are keyed by API key, so switching accounts can never serve another account's cached data. The cache lives in the layer and is shared across open project directories — acceptable because the underlying config (`skills.urls`) is global; revisit if per-directory repo sources are ever introduced.
- Tarball downloads are capped at 20MB **compressed** (Content-Length pre-check plus actual buffered length), with `MAX_EXTRACTED_BYTES` remaining the post-decompression second line of defense against zip bombs. A disk cache was considered but skipped to avoid cache-invalidation and partial-write complexity.
- The SDK OpenAPI spec gains new endpoints under `/api/skill/`. The JS SDK must be regenerated via `./packages/sdk/js/script/build.ts` if the spec changes.
- SkillHub metadata comes from the list API's `displayName`/`summary` fields directly; the marketplace does **not** download `SKILL.md` per skill for browsing (an earlier draft of this ADR required that — superseded once the list API proved to carry display metadata).
- SkillHub credentials reuse the existing `Auth.Service` (providerID `"skillhub"`); requests are anonymous when no key is configured. The previously hardcoded bearer token in `skillhub.ts` is removed. Keys are validated against `GET /api/v1/auth/me` before being saved (verified by probing: 200 for a valid API token, 401 for invalid/anonymous). Note `/api/web/me/**` is cookie-session-only and returns 403 for every API token, so it cannot be used for validation or "my skills" listing from the CLI. **Consequence**: the "configure API key" entry in the marketplace UI (app and TUI) is commented out — a configured key cannot surface private skills in the catalogue, so the entry would be misleading. The `setSkillHubKey`/`removeSkillHubKey`/`skillHubStatus` service methods and HTTP endpoints remain for direct API use.
- Private skills never appear in any list endpoint. With a configured token they are resolvable by direct slug lookup (`GET /api/v1/skills/{namespace}/{slug}` → `headlineVersion`), and their `files`/`file`/`download` endpoints return 200 for the owner — verified with a live PRIVATE probe skill. `findSkillHubItem` therefore falls back to a direct slug lookup when the public catalogue doesn't contain the name.
- Installs must invalidate the one-shot `Skill.Service` discovery state, otherwise a freshly installed skill is unusable until restart (the "looks installed but isn't" failure mode).
- The HTTP surface uses action-oriented POST endpoints (`/api/skill/marketplace/install`, `/api/skill/marketplace/uninstall`, `/api/skill/repos/add`, `/api/skill/repos/remove`) rather than the REST-style DELETE endpoints sketched in the original plan, plus key management as GET/PUT/DELETE on `/api/skill/skillhub`. Nine endpoints total under `/api/skill/`.
- All file writes during install pass through a single choke point (`writeSkillFiles`), which rejects any unsafe relative path (`..`, absolute, backslash, empty) with an `InstallError` instead of silently skipping — this covers SkillHub-sourced files, whose paths come from a remote server and are not pre-filtered the way tarball entries are.
- Tarball gunzip uses `node:zlib`'s `gunzipSync` rather than Bun's native API, because the desktop server runs under Node; `node:zlib` works under both runtimes.
- Repo sources are strictly opt-in: no default GitHub/Gitee repos are bundled or injected on first launch (the plan's optional Task 8 was dropped). An empty `skills.urls` simply means no repo sources.
- `parseRepoUrl`/`SkillRepo` live in `skill/repo.ts`, a pure module with no HTTP imports, so the startup-sensitive `skill/index.ts` can classify repo URLs without pulling in the marketplace's HttpClient stack.
