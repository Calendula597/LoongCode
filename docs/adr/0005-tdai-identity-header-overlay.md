# TDAI identity switching uses per-identity proxy session headers, not a TDAI-side switch API

For the experimental TDAI integration, a LoongCode Session bound to one TDAI task may switch its active TDAI Identity freely mid-session. The MemoryProxy fixes a session's identity at init time and offers no mid-session identity change, so each TDAI Identity carries its own complete header set — task scoping (`x-team-id`/`x-agent-id`/`x-task-id`) plus its own Proxy Session Key (`x-conversation-id`) — and LoongCode injects the active identity's headers verbatim into requests to the base provider. Switching identity simply means the next request goes out with a different header set; the proxy auto-registers each header set as a distinct session via its existing preset-identity path, with no interactive form and zero TDAI changes. Identities are pure header overlays on one shared base provider entry: they never pin a model, so model selection stays free and an identity switch alone does not replace the Context Epoch.

## Considered Options

- TDAI-side switch-identity API (mutate SessionStore agent_id + refresh injection cache): rejected for v1 — cleaner semantics, but requires landing and deploying a MemoryProxy change before LoongCode can iterate.
- Per-request identity header override in the proxy request hot path: rejected — highest flexibility but touches every proxied request's attribution logic; too risky for an experiment.
- Interactive re-init form on switch: rejected — LoongCode has no adapter for the proxy's AskUserQuestion-style form flow, and mid-session forms would break non-interactive runs.
- Computed composite session key (`<sessionID>:<agentID>` generated by LoongCode): rejected in favor of verbatim configured headers — the panel-configured `x-conversation-id` per identity is simpler, matches existing hand-rolled configs, and keeps memory continuity per identity across LoongCode Sessions when desired.

## Consequences

- The proxy sees one session record per identity rather than per LoongCode Session; proxy-side session listings and per-session metrics fan out accordingly. Two LoongCode Sessions using the same identity share one proxy session (memory continuity by design; give identities distinct `x-conversation-id` values to avoid it).
- Identity validation and task-agent linking are skipped in v1, so a mistyped header value silently creates a new proxy session and memory namespace; validation via TDAI metadata (exists, same team, auto-link) is the documented follow-up.
